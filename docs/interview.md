## 开场

“深圳现场要两块电源板。如果仓库已经扣了库存，但 Agent 收到 504，它应该再发一次吗？你可以在这三个按钮里挑一个，跑完一起看账本。”让对方自己选，再打开轨迹里两次调用的工单号和幂等键。

## 现场依次看三件事

| 时段 | 怎么操作 | 能看到的工程判断 |
| --- | --- | --- |
| 0–25 秒 | 默认工单，比较直接重发与先查回执 | 直接重发用新键占 4 件。核验策略先按原单查到 WH-001，账本只占 2 件。业务验收要看实际库存 |
| 25–55 秒 | 把故障换成“写入前超时”，再把预算调到 0 | 相同的 504 也可能发生在提交之前。回执为空且预算为零，系统能明确报告未预留。若回执服务离线，系统会保留“待人工核验” |
| 55–90 秒 | 评测页找 D27，点回实验台 | 首版把“先别预留”误作写入。当前版只执行两个读工具，给出 14:35 到货的报价，库存完全保留 |

## 面试官可能追问

**“为什么不一直用同一个幂等键重试？”** 在本项目的仓库契约下，这个办法可行。9 组额外对照中，写入前超时用原键直接重试只需两次请求，先查再写需要三次。回执服务离线而写接口仍支持重放时，原键重放也能拿到成功回执。选择策略前要向仓储方确认哪些接口支持持久幂等、键多长时间过期、相同键和不同参数会怎样处理。[9 组完整记录](../bench/idempotency-results.json)

**“36/36 有没有刷题？”** 这是随项目固定并参与改进的回归集，覆盖具体契约。它证明改动后已发现的问题没有重现。自然语言泛化和供应商模型表现需要另备未见工单及真实模型批次。两组指标应分别陈述。

**“仓库没查到回执，是不是一定没写入？”** 演示仓库承诺写入和回执原子更新，查询具备读己之写一致性。接真实 WMS 时，如果查单走延迟从库，空结果可能是暂时不可见。需要幂等写、持久业务号以及延迟复查的业务约定，才能定义自动恢复边界。

**“你真正交付了什么？”** 一个公开可交互的故障实验台、可在本机启动的两个 HTTP 服务、四个 LangChain 工具、三策略对照、36 个带答案的验收案例、9 个幂等写实验，以及每次运行可下载的请求和账本。公开版为模拟业务环境，不代表企业生产上线或节省了实际成本。

## 简历可选写法

**Agent 应用开发方向**

基于 LangChain JS 实现库存、到货估算、备件预留与回执核验 4 个结构化工具，按写入授权、幂等键和重试预算编排工具调用。构建 36 条合成工单回归集，以工具路径及真实模拟账本验收，确定性核验流程端到端通过数由 28 提升至 36。

**FDE / AI 应用交付方向**

将“不重复占货、按时交付、结果可核验”拆为可执行验收条件，搭建双仓 HTTP 服务与公开故障演示台。在 2 件调拨工单的回执丢失场景复现实际占用 4 件（多占 2 件），采用按单核验后保持 2 件，支持逐步回放与验收记录导出。
